## Current goal

Implement the first small Core API foundation:

# Zone + Vehicle

These resources are prerequisites for passenger ride requests and driver/pool functionality.

The existing Prisma schema already contains `Zone` and `Vehicle`. Inspect the actual schema before coding and use the existing fields/relations exactly as defined.

---

# PART A — Zone API

Zones represent the predefined Dhaka pickup/destination areas used by the MVP.

The challenge explicitly says we should keep geography simple and use predefined Dhaka areas.

Do NOT integrate Google Maps, Mapbox, routing APIs, geocoding APIs, or external geographic services.

### Required endpoints

Implement:

```http
GET /api/v1/zones
GET /api/v1/zones/:id
```

Use the existing project route/module structure.

### GET /zones

Return available predefined zones.

Use the existing standard response structure.

### GET /zones/:id

Return one zone by ID.

If the zone does not exist, use the project's existing error conventions.

### Rules

* Zones are readable without authentication unless the existing architecture strongly suggests otherwise.
* Do not add zone creation/update/delete endpoints yet.
* Do not allow arbitrary user-created zones.
* Do not modify the Prisma schema.
* Do not add external map services.

---

# PART B — Vehicle API

Vehicles represent the driver's Tesla/Bullet.

The vehicle belongs to a driver.

Inspect the actual `Vehicle` Prisma model and use its real fields and relations.

### Required endpoint

Implement the minimum driver vehicle creation/read flow needed for the MVP.

At minimum:

```http
POST /api/v1/vehicles
GET /api/v1/vehicles
GET /api/v1/vehicles/:id
```

Use existing authentication and authorization middleware.

Expected route protection:

```text
POST /vehicles
    ↓
authMiddleware
    ↓
requireRole(DRIVER)
    ↓
controller
```

The authenticated driver's ID must come from:

```ts
req.user.id
```

Never trust a client-supplied driver/user ID.

---

# Vehicle ownership

A driver must only be able to access their own vehicle data where the endpoint represents their personal vehicle resource.

Use the existing:

```ts
assertOwnership()
```

helper where appropriate.

Do not create another ownership utility.

A passenger must not be able to create or modify a driver's vehicle.

---

# Vehicle capacity

The challenge says Bullet has a fixed capacity and the system must never exceed capacity later in the pooling flow.

Inspect the current schema and preserve the existing capacity representation.

Do not create dynamic capacity logic yet.

For this task, simply ensure the vehicle stores the fixed capacity required by the existing model/business rule.

Do not allow arbitrary passenger-controlled capacity values.

If the existing application design requires the capacity to be assigned server-side, do that.

Document the assumption if necessary.

---

# Validation

Use the project's existing Zod validation conventions.

Inspect existing validation schemas first.

Validate only fields actually present in the current Prisma `Vehicle` model and required by the MVP.

Do not duplicate Prisma enums or types manually.

---

# Business rules

At minimum enforce:

1. Only authenticated DRIVER users can create a vehicle.
2. A vehicle must have an owner/driver according to the existing schema.
3. A driver cannot accidentally create a vehicle for another driver.
4. A passenger cannot create a vehicle.
5. Vehicle lookup must respect ownership where appropriate.
6. Use existing AppError and ERROR_CODES.
7. Do not leak Prisma errors directly to clients.

If the current schema already has unique constraints such as vehicle plate uniqueness, rely on those constraints and convert expected conflicts into the project's standard application-level error where necessary.

Do not add unnecessary abstractions.

---
